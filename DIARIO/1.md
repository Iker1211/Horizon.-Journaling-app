## 2. Diseño de Base de Datos para Miles de Usuarios
En aplicaciones proyectadas para alto tráfico y escalabilidad:

* **Almacenamiento temporal estricto (`TIMESTAMPTZ`):**
  * Las fechas nunca se almacenan como texto plano en producción. Se usa `TIMESTAMPTZ` (Timestamp with Time Zone) normalizado en **UTC**.
  * El navegador del usuario recibe la marca UTC y la formatea localmente a su zona horaria (`Intl.DateTimeFormat`).
* **Diferencia entre marcas temporales:**
  * `created_at`: Marca técnica e inmutable sellada por el servidor PostgreSQL (`DEFAULT timezone('utc', now())`).
  * `published_at`: Momento en que el contenido se hace visible al público (puede ser nulo si es un borrador o posterior si es programado).
  * `updated_at`: Última modificación.
* **Indexación de alto rendimiento:**
  * Para que miles de usuarios consulten y ordenen sus entradas sin degradar el rendimiento, se implementa un índice compuesto B-Tree:
    ```sql
    CREATE INDEX idx_blog_entries_user_created 
      ON public.blog_entries (user_id, created_at DESC);
    ```
  * Esto reduce el tiempo de búsqueda a $O(\log N)$ evitando escaneos completos de la tabla (*full table scans*).

## 3. Privacidad y Row Level Security (RLS) en Supabase
* **Seguridad en el Kernel de la Base de Datos:**
  * La privacidad no depende de filtros en JavaScript en el frontend.
  * Se delega a las políticas RLS de PostgreSQL:
    ```sql
    CREATE POLICY "Users can manage their own blog entries"
      ON public.blog_entries
      FOR ALL
      USING (auth.uid() = user_id)
      WITH CHECK (auth.uid() = user_id);
    ```
* **Navegador sin memoria (*Stateless* / Modo Incógnito):**
  * Aunque el navegador no tenga `localStorage` ni memoria previa, la identidad se envía mediante el token en la petición HTTP.
  * La consulta se puede hacer bajo demanda (*Lazy Fetch*): la fecha de redacción solo viaja por la red cuando el usuario dueño de la entrada la solicita explícitamente.

## 4. Anatomía de la Autenticación con Tokens JWT
* **En la cabecera HTTP:**
  * El cliente envía el token en cada petición:
    `Authorization: Bearer <header>.<payload>.<signature>`
* **Dentro del token (El Payload):**
  * La variable `user.id` está representada bajo el estándar **`sub`** (*Subject*):
    ```json
    {
      "sub": "3f4a9a08-1b2c-4d3e-8f90-123456789abc",
      "role": "authenticated",
      "exp": 1788825000
    }
    ```
* **Cómo lo lee PostgreSQL:**
  * La función `auth.uid()` de Supabase es un atajo interno que extrae el `sub` de la cabecera:
    `current_setting('request.jwt.claims', true)::json->>'sub'`

## 5. Peticiones HTTP vs. WebSockets

| Característica | Peticiones HTTP | WebSockets |
|---|---|---|
| **Modelo** | Petición - Respuesta (*Pull / Unidireccional por intercambio*) | Canal persistente bidireccional (*Push / Full-Duplex*) |
| **Conexión** | Se abre y se cierra por cada intercambio. | Se negocia una vez (handshake) y queda abierta. |
| **Iniciativa** | Siempre la toma el cliente. El servidor no puede iniciar contacto. | Ambos pueden enviar mensajes en cualquier milisegundo. |
| **Sobrecarga** | Reenvía cabeceras y tokens en cada petición. | Mínima sobrecarga; viajan datos crudos en paquetes ligeros. |
| **Uso en la app** | Guardar entradas, login, consultas CRUD normales. | Sincronización en tiempo real entre múltiples dispositivos (Supabase Realtime). |

### Verbos HTTP principales:
* **`GET`**: Lectura segura e idempotente.
* **`POST`**: Creación de recursos o envío de datos para procesamiento.
* **`PUT`**: Sustitución completa de un recurso.
* **`PATCH`**: Modificación parcial de un recurso existente.
* **`DELETE`**: Eliminación de un recurso.

## 6. La Firma Criptográfica y el `JWT Secret`
* **¿A qué está atada la `JWT Secret`?**
  * **Al PROYECTO / SERVIDOR**. No a la sesión, no al usuario, ni a la petición individual.
  * Es la clave maestra privada que solo reside en los servidores de Supabase.
* **¿Cuándo se genera la firma?**
  * **En el momento del LOGIN** (una sola vez por sesión).
  * El servidor calcula: $\text{Firma} = \text{HMAC-SHA256}(\text{Header} + \text{Payload}, \mathbf{JWT\_Secret})$.
* **¿Qué hace cada petición HTTP posterior?**
  * El navegador **no firma nada** (no conoce el secreto). Solo adjunta el token ya firmado.
  * El servidor **solo verifica**: vuelve a calcular la firma con su `JWT Secret` y comprueba si coincide con la firma recibida.
* **Analogía del Notario:**
  * `JWT Secret` = El cuño o sello oficial bajo llave del notario.
  * `Payload` = Tus datos escritos en el papel.
  * `Firma` = La marca de tinta física estampada en el documento.
  * `Login` = El día que te sellan el documento en la notaría.
  * `Petición HTTP` = Mostrarle el documento sellado al guardia para entrar. El guardia no fabrica un sello nuevo, solo verifica que la tinta y el cuño sean legítimos.

## 7. Criptografía: El Efecto Avalancha y la Imposibilidad del Hackeo
* **El Efecto Avalancha (*Avalanche Effect*):**
  * Propiedad fundamental de las funciones hash (como SHA-256).
  * Si un atacante cambia un solo bit (un `0` por un `1`, o una letra del `user.id`), **más del 50% de la firma resultante cambia de forma caótica e impredecible**.
* **El dilema sin salida del atacante:**
  * Si el atacante altera el `user.id` en el Payload, la firma original queda invalidada al instante.
  * Para que el servidor lo acepte, el atacante necesitaría calcular la nueva firma correspondiente al dato alterado.
  * Para calcular esa nueva firma, la matemática exige obligatoriamente la `JWT Secret`.
  * Como no tiene la `JWT Secret`, la comprobación en el servidor falla en 0.2 milisegundos arrojando:  
    `401 Unauthorized: Invalid Signature`.
* **Funciones Hash vs. Números Primos:**
  * **Funciones Hash (SHA-256 / HMAC):** Operaciones de rotación y mezcla binaria de una sola vía (*one-way*).
  * **Criptografía Asimétrica (RSA / HTTPS):** Basada en la dificultad matemática extrema de factorizar números que son producto de números primos gigantescos de cientos de dígitos.
